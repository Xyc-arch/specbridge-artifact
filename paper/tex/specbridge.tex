\begin{abstract}
A text-to-SQL answer can run, return a plausible number and still compute something other than what the analyst meant. This happens when a request leaves a calculation choice open, such as whether to count rows or entities, and the model settles the choice without saying so. Benchmarks cannot detect this, because they score one reference reading even where the question leaves the choice open. This paper introduces \system{}, a framework that tests what a model does with such a choice by changing only that choice. A request set holds three requests on the same data, one for each of two readings and one that leaves the choice open, and execution scores every answer. \system{} builds request sets on real databases from choices mined from benchmark failures. On 204 hand-validated request sets, four models usually compute both readings when each is asked for, yet for the open request they return both readings in only 16--58\% of those sets, and they seldom say that a choice existed. When they settle a choice silently, they take the reading that benchmark references take by convention, and on BIRD over two in five of the answers scored wrong on such questions return the other reading. Two design rules make answers more reliable: show an alternative only when its result differs, which is 19 points more precise than rewriting the request once per reading, and clarify a request by adding one clause rather than rewriting it.
\end{abstract}

\section{Introduction}
\label{sec:intro}
Analysts increasingly ask for numbers in natural language and get them from a text-to-SQL system, often without reading the SQL. For these users a query that fails is safe, because the error is visible. The dangerous answer is a query that runs and returns a plausible number, computed differently than the analyst meant. Outside SQL, such small calculation choices have had large consequences. A finding that high public debt slows growth depended on averaging within each country before averaging across countries~\cite{herndon2014debt}, and a health-care algorithm that measured need by cost cut the Black patients chosen for extra care by more than half~\cite{obermeyer2019bias}. Hospital mortality ratings depend on which discharges count~\cite{shahian2010mortality}, and twenty-nine teams given the same data on referees and skin tone reached different conclusions~\cite{silberzahn2018many}. A text-to-SQL system makes such choices on every request, and its user sees only the result.

Take ``the average rental price per day'' for each film rating (Figure~\ref{fig:teaser}). It can be computed two ways, which we call readings: A averages each film's daily price; B divides the average price by the average rental length. For two films priced at \$6 for two days and \$6 for six days, the first reading gives \$2.00 per day and the second \$1.50. Both are simple SQL, and on the \texttt{sakila\_1} database the two readings differ for every rating. For the request as worded, which leaves this choice open, all four models we test, Claude Haiku~4.5, Claude Sonnet~5.5, GPT-6 Sol and GPT-6 Luna (Haiku, Sonnet, GPT-Sol and GPT-Luna below), return A; only Sonnet also says that there is a choice and gives B, the ratio of two averages.

A reliable text-to-SQL system must do three things: compute the reading that a specific request asks for, report a choice that a request leaves open together with the other reading, and stay quiet about a choice that the wording already settles. Benchmarks such as Spider and BIRD measure only the first. They score each question against one reference reading, even where the question leaves the choice open, so a model that guesses the authors' reading scores as well as one that reports the choice. Ambiguity benchmarks~\cite{ambiqt2023,ambrosia2024} score whether a model's outputs contain every reading of an ambiguous question. They cannot separate a model that cannot compute a reading from one that computes it but stays silent, and they do not penalize raising a settled choice (Table~\ref{tab:comparison}).

Our key idea is to change only the choice. For each test we write three requests on the same database: a specific request for reading A, a specific request for reading B, and the open request, which leaves the choice open. With the two reference queries they form a request set. Because the three requests differ only in the choice, each failure has one cause: the model cannot compute a reading, computes one but picks the other, or computes both but does not tell the user. For the open request, the model states its assumptions and may give SQL for other readings; offering the other reading for a specific request is a false alarm, as the wording settles it.

Building request sets at scale is hard for three reasons. First, a test must control what each query computes and describe it exactly, on databases that nobody has annotated. Second, the choices must be ones that matter in real requests, not invented ambiguities. Third, the three requests must differ only in the choice, yet a rewritten request easily changes other requirements. \system{} addresses each in turn. It generates SQL from a catalogue of column meanings under type rules, and code describes each query exactly in words (Section~\ref{sec:construction}). It mines choices from BIRD and Spider questions that models fail as worded but answer correctly from an exact description of the reference SQL, and keeps only edits that change the answer on the data (Section~\ref{sec:library}). It writes the three requests from one list of shared requirements, and code, two reviewer models and an author check every set (Sections~\ref{sec:apply} and~\ref{sec:specresults}). Execution, not a model, decides every accuracy score.

\textbf{Finding 1: Models make choices without saying so} (Section~\ref{sec:disclosure}). On 204 accepted request sets, the models answer both specific requests correctly in most sets, but on the open request they return both readings in only 16--58\% of those sets. Most missed readings are ones the same model computes correctly when asked for them alone, so the gap lies in reporting, not in computing. When a model settles a choice silently, it takes the reading that benchmark references take by convention, the reading benchmarks reward.

\textbf{Finding 2: Benchmarks cannot see the gap} (Section~\ref{sec:diagnosis}). When the wording of a BIRD or Spider question does not settle a choice, the reference SQL still takes one reading, by a convention of its author group. BIRD and Spider's own authors return one row when several tie and count joined rows, while the questions Spider imported from older datasets reverse one of these conventions each. The choice is not cosmetic: on BIRD, nearly one in four questions that leave a choice open changes its answer under the other reading, and over two in five answers BIRD marks wrong give that reading.

\textbf{Finding 3: Two design rules make answers more reliable} (Section~\ref{sec:method}). Most requests are clear, so a system must not add wrong alternatives to them. Answering each reading separately and showing an alternative only when its result differs is 19 points more precise on AMBROSIA than disambiguate-then-parse (DtP)~\cite{saparina2025disambiguate}, which rewrites the request once per reading, at a third of its calls. When the user settles a choice, the system should keep the request and add one clause, because a rewritten request loses other requirements, such as an output column or a join.

In summary, we make three contributions: (1) request sets, controlled tests that change one calculation choice and are scored by execution, with a generator that builds them on real databases and a library of choices mined from benchmark failures (Sections~\ref{sec:framework}--\ref{sec:evaluation}); (2) three findings on four models across our request sets, AMBROSIA and BIRD (Sections~\ref{sec:disclosure}--\ref{sec:diagnosis}); and (3) two design rules for reliable answers, each tested against the closest alternative (Section~\ref{sec:method}). We release the generator, the 307 request sets with the author's verdicts, all model responses, and a package that reproduces every number in this paper without new model calls; a supplement gives the generator's details, the full library and recorded responses.
\section{\system{} Overview}
\label{sec:framework}
\system{} turns a database into request sets in two lanes that meet in one step (Figure~\ref{fig:pipeline}). The first lane generates queries whose computation is known exactly. The second lane mines, from benchmark failures, the choices that real requests leave open. The last step applies one such choice to a generated query and writes the three requests. We first follow two request sets through this process (Section~\ref{sec:worked}) and then describe each step: generating queries (Section~\ref{sec:construction}), mining choices (Section~\ref{sec:library}), and building request sets (Section~\ref{sec:apply}).

\subsection{Two examples}
\label{sec:worked}
\label{sec:test}
A request set fixes a database and every requirement of a query but one choice. The film request of Figure~\ref{fig:teaser} asks for each rating's average replacement cost and daily rental price, and compares that daily price with the average across ratings. Only the daily price is open:
\begin{equation}
 A=\operatorname{AVG}(\text{price}/\text{days}),\qquad
 B=\frac{\operatorname{AVG}(\text{price})}{\operatorname{AVG}(\text{days})}.
\end{equation}
A averages each film's daily price; B divides two averages and so gives more weight to longer rentals. The specific request for A asks for the average of per-film daily prices, the one for B asks for the average price divided by the average duration, and the open request asks for the ``average rental price per day.'' The rest of the wording is shared, and code checks that the two queries return different results on the database; a choice that does not change the answer is not tested there. \label{sec:additionalexample}The second example (Figure~\ref{fig:worked}) is a three-step query on the \texttt{insider} database. It averages short-interest measurements for each transaction, compares each transaction with a baseline for its order type, and returns the ten largest ratios. The choice lies in the baseline: A averages the transaction means, so each transaction counts once, while B averages the underlying snapshots, so a transaction with more snapshots weighs more. The open request asks for ``the average short interest for its order type mix,'' and all ten output rows change between the readings.

\subsection{Generating queries}
\label{sec:construction}
\label{sec:querygen}
\label{sec:writing}
Generation starts from the database, not from a benchmark, so it works on databases nobody has annotated. One model review of the schema and data first builds a catalogue of column meanings, units and table relationships; after that, generation calls no model. A query starts from counts, sums or averages per entity, per group or overall. Later steps can compare a value with a broader average, take a share of a total, combine compatible quantities, aggregate again, or keep the top entities per group. We control two properties of each query: arithmetic depth, the nesting of arithmetic expressions, and step depth, the number of dependent query stages. Type rules decide which quantities can be combined or summed, and data checks reject empty answers, constant or redundant quantities, non-positive denominators and too-small groups. To reach a requested depth without trial and error, the generator looks ahead: it drops a partial query as soon as no completion of it can reach the requested depths and operations, so attempts are not spent on dead ends.

Code then describes each query exactly in words. The text covers source rows, joins, unmatched rows, filters, groups, formulas, missing values, ordering, limits, ties and SQLite conventions, and the same SQL always gives the same text; we call it the exact description. Because the exact description states every requirement, a model that fails from it cannot compute the query, while a model that succeeds from it but fails from a natural request was misled by the wording. Section~\ref{sec:library} builds on this contrast. A writer model turns the exact description into one natural request, using the column meanings. A second model checks the request for missing, changed or added requirements, and code checks how stored values are written. A failing request gets one revision and is dropped if it fails again.

\subsection{Mining choices from benchmark failures}
\label{sec:library}
The choices come from real benchmark failures. For each BIRD and Spider question, we compare a model's answer to the original question (with BIRD's evidence) with its answer to the exact description of the reference SQL. When only the description is answered correctly, the wording caused the failure, not the model's SQL, and we look for the reason: output columns, a different column or value, an unstated requirement, numerical precision, or an open choice. For an open choice, the other reading is written as an edit of the reference SQL, and both queries are executed. Two reviewer models judge each reading independently, and disagreements are kept. The library keeps choices of meaning, both open ones, where the wording fits both readings, and settled ones, where it selects one. For ``What is the total number of molecules with double bonded oxygen?'', both reviewers accept only the reading in which the oxygen atom is part of the double bond, although the reference SQL counts every molecule that contains an oxygen atom and a double bond. Figure~\ref{fig:choices} groups the library by choice type. The largest group of open choices concerns which column a phrase refers to, and half of the settled ones concern the counting unit.

The same choices appear in benchmark references, and the references do not agree on them. We call a question silent on a choice when neither its wording nor BIRD's evidence contains a word that settles it, such as ``all'' for ties or ``distinct'' for counts. For 12 of the 13 choice types, code reads which reading a reference takes, and Figure~\ref{fig:choices} counts the silent BIRD and Spider questions and the share whose reference takes the rarer reading. Every case of the rarer reading was reviewed and only confirmed cases are counted, so these shares are conservative. The split is real: 12.3\% of silent tie questions return every tied row, and 8.6\% of silent counts over a join count distinct entities. For these choices, a benchmark that scores one reading treats a convention as the only correct answer.



\subsection{Building request sets}
\label{sec:apply}
\label{sec:filters}
A request set needs a choice that matters on the data, so code first reports where a generated task's columns have missing values, repeated join matches, distinct values or ties. A writer model proposes one choice from the library and an exact SQL edit for it, and code checks that the edit applies, runs, changes the answer and can still be described exactly; a failed proposal gets one repair. The writer then writes the request set from a plan that lists the shared requirements and the one differing choice: the request for A, an edit of it for B, and the open request. A library example of the same type may guide the wording, but never supplies the SQL. Two reviewer models check that the requests keep their requirements and judge each of the three requests against each reading. A set is kept only when both reviewers accept each specific request for its own reading alone and at least one accepts the open request for both readings. Five library types concern a filter, such as whether a cutoff is strict. Generated queries seldom filter, so for these types the generator adds one condition chosen from the data, which keeps 20--80\% of the rows. Figure~\ref{fig:choices} gives an example of each type. The pipeline keeps 307 request sets on 12 databases, and an author accepts 204 of them by hand (Section~\ref{sec:specresults}); every result below uses these 204.

\section{Measures}
\label{sec:metrics}
We score what a model computes by execution and what it says by a model judge. A specific request selects one reading, and the open request fits both. A choice is settled when the wording selects one reading. We execute every returned query and compare its result with the reference result, with numerical tolerance and with rows tied at a cut-off treated as interchangeable; an execution error scores zero, as in Spider and BIRD scoring. For benchmark questions we also report a score that allows extra or reordered output columns.

For the open request, the model returns a main query and up to two alternatives. The model returns both readings when these queries include one with the result of A and one with the result of B. We report this share over all sets and over the sets in which the same model answers both specific requests correctly, where a miss cannot be a failure to compute. Written as a formula, with $S_i$ the queries returned for the open request of set $i$, $e(p,\hat p)=1$ when query $\hat p$ returns the result of reference $p$, and $B_i=1$ when both specific requests are answered correctly,
\begin{equation}
\mathrm{Both}=\frac{\sum_i B_i\prod_{j\in\{A,B\}}\max_{\hat p\in S_i}e(p_j,\hat p)}{\sum_i B_i}.
\end{equation} A missed reading is computable when the same model answers the specific request for it correctly. A model names the choice when its explanation says that the choice is open, whether or not it gives SQL for the other reading. A judge model, which does not know which model answered, decides whether a response names the choice and whether its stated reading matches its SQL. For a specific request, offering the other reading, or calling the choice open, is a false alarm. The measures check one another. Returning both readings alone would reward a model that adds every alternative it can think of, and the false alarms charge for that; naming alone would reward a warning without an answer, and returning both readings charges for the missing query. \section{Experimental Setup and Test Checks}
\label{sec:evaluation}
Sections~\ref{sec:disclosure}--\ref{sec:method} answer three questions: do models report the choices they make, can benchmarks see whether they do, and how should a system disclose a choice and carry a clarification? This section describes the setup (Section~\ref{sec:setup}) and checks that the tests change only the choice (Section~\ref{sec:specresults}).

\subsection{Experiment settings}
\label{sec:setup}
\textbf{Databases and questions.} Request sets use 12 databases, four each from Spider (baseball, Sakila, customers-and-invoices, Chinook), BIRD development (financial, student club, thrombosis prediction, Formula 1) and LiveSQLBench\footnote{\url{https://github.com/bird-bench/livesqlbench}} (archeology, insider, crypto, alien). The generated tasks request arithmetic depth 1--2 and step depth 3--6, and each database contributes 12 to 24 accepted request sets. The BIRD analysis uses 481 development questions on five databases and holds out 100 before the final evaluation; the Spider analysis uses 150 development questions and holds out 50. We also use the AMBROSIA test split, with ambiguous and unambiguous questions.

{\sloppy\textbf{Models.} We evaluate Haiku, Sonnet, GPT-Sol and GPT-Luna (\texttt{claude-haiku-4-5}, \texttt{claude-sonnet-5-5}, \texttt{gpt-6-sol}, \texttt{gpt-6-luna}). Claude Opus~5.5 writes and reviews the requests and judges the explanations, with Sonnet as the second reviewer; it is not evaluated. Models see the schema and documentation and have no file or tool access. By default a model answers in one call, with a prompt that asks for SQL, for a brief statement of ``any consequential assumption that the request and the supplied context do not settle,'' and for SQL of any other supported reading, without inventing alternatives (the explain prompt). To test whether a model can compute a reading at all, we give it its best chance and let it explore: it may first run up to six rounds of five queries on the database, seeing twenty rows of each result. Exploration changes little; GPT-Sol answers 59 of 100 original BIRD questions correctly without it and 61 with it, so it does not explain the results below.\par}

\textbf{Statistics and baselines.} Intervals resample tasks 2,000 times, keeping pairs together; proportions use Wilson intervals; paired comparisons use exact McNemar tests. For the disclosure method (Section~\ref{sec:method}), we compare with the AMBROSIA authors' prompt, the same prompt sampled three times at about the method's cost, and disambiguate-then-parse~\cite{saparina2025disambiguate}.



\subsection{Checks on the tests}
\label{sec:specresults}
\label{sec:resconstruction}
\label{sec:writerswap}
The findings rest on tests that change only the choice, so we check the tests first. Code confirms that in every set the two queries differ in one step and the two specific requests differ only in the choice phrase. An author then read every set without seeing model results and asked whether a reasonable analyst could mean either reading. Most rejected sets have an open request whose wording already favours one reading. A choice can look open and still be settled by convention: every date-range request says ``between,'' which SQL's \sql{BETWEEN} includes, and 254 of the 255 BIRD and Spider references whose question says ``between'' with no other cue include both ends, so the author rejects all 17 date-range sets. A set must also test a choice on which real references differ, so we reject the sets of choice types that fewer than 1\% of silent references read the other way. This leaves 204 of the 307 sets; they test aggregation level, cutoffs, ties, counting units, missing values and one negation. Figure~\ref{fig:funnel} shows what each stage keeps: most proposed choices change the answer and can be described, and the largest cuts come from keeping one choice per task and from the author's review.

The generator itself is reliable. Its rules find usable queries on 152 of 190 databases; the others lack the repeated rows the rules need. On the 12 evaluation databases it delivers 1,198 of 1,200 requested queries, all at the requested depths, and each of its rules is needed (Figure~\ref{fig:ablation}): without the look-ahead, almost no attempt reaches its target. Natural requests also lose little against exact descriptions (Figure~\ref{fig:specification}). Sonnet and GPT-Sol lose about two points, and Haiku and GPT-Luna do better with natural wording. Because Sonnet writes every natural request and is also evaluated, GPT-Sol wrote a second version of 200 random tasks; measured against the two models that wrote neither, neither writer favours itself. Writing from a plan is what keeps the three requests aligned: on 60 fixed tasks, it keeps the shared requirements in 52 drafts, against 32 for direct generation ($p=0.0002$), and passes all checks in 49 against 32.

\section{Models Make Choices Without Saying So}
\label{sec:disclosure}
A model that computes both readings when each is asked for usually returns only one of them for the open request, and seldom says that there was a choice. Asking for an explanation does not cause this gap. Against the same call asking only for SQL, correct answers to specific requests change by at most three of 204 per model, and every paired interval includes zero. Nor does it make models raise settled choices: the judge finds at most two of 204 responses to specific requests per model that call the choice open. The explanation costs time: the median request takes 7.5--50.0 seconds per model with it, against 4.3--17.9 seconds for SQL alone.

\begin{figure}[t]
\centering\includegraphics[width=\columnwidth]{col_disclosure.pdf}
\caption{Answering and communicating on 204 request sets (95\% intervals).}
\Description{Dot plot of five measures for four models with 95 percent intervals.}
\label{fig:disclosure}
\end{figure}

\textbf{Models return one reading where two are correct.} Returning both readings is much rarer than returning one correct answer (Figure~\ref{fig:disclosure}). Even among the sets in which a model answers both specific requests correctly, it returns both readings for the open request in only 58\% for Sonnet, 45\% for GPT-Sol, 31\% for Haiku and 16\% for GPT-Luna. What the models do state is accurate: a stated reading matches the model's SQL in 99--100\% of responses. The models describe one calculation correctly without saying that another, equally valid calculation was possible on the same data.

\textbf{The gap does not come from how we selected the sets.} On the 161 sets built without a filter the range is 10--51\%, and on all 232 sets before the 1\% rule on choice types 15--56\%. The unreported reading matters: in 98 of the 204 sets, the two readings return different rows, and in the other 106 the same rows with different computed values, so the user gets a different answer in every set.

\textbf{Most misses are failures to report.} Most readings a model misses on the open request are ones it can compute. The same model computes the missed reading correctly when asked for it alone in 66--94\% of the missed sets (Figure~\ref{fig:decomposition}). Figure~\ref{fig:outcomes} sorts every open request into four outcomes: both readings returned; the choice named but one reading given; one reading given silently although the model computes both; and a reading the model does not compute. For Haiku and GPT-Luna the most common outcome is the silent one, in which the model can compute both readings but gives one without naming the choice, and for Sonnet and GPT-Sol it is the second most common. A score that only checks whether both readings appear among the outputs, as top-$k$ coverage~\cite{ambiqt2023} does, cannot tell these outcomes apart. Sampling does not surface the other reading either: five SQL-only samples contain both readings in at most 16 of 55 sets for any model, while one explained response from Sonnet does so in 34: what is missing is a prompt to report the choice, not more samples of the same answer from the model.

\textbf{The gap is widest for choices inside a calculation.} Sonnet, the best model, returns both readings for 68\% of aggregation-level sets but for only a third of tie and counting-unit sets, and the other models do worse (Figure~\ref{fig:bytype}). These are the choices that hide in the SQL: a \sql{LIMIT}, a \sql{COUNT} over a join, or an average taken at one level, none of which the request mentions. Cutoffs are the exception: most cutoff requests give a value ``as the cutoff'' with no comparison word, which invites both the strict and the inclusive reading. The gap holds on every source of databases: no model returns both readings for more than 67\% of the sets from any source.

\textbf{Naming a choice is not the same as giving the other reading.} A model that says a choice is open often stops there. Among the sets in which a model names the choice and can compute both readings in the same call, it still returns only one reading in 14--61\% of them, and GPT-Luna does so most often. Such a response warns the user but leaves them to write the other query, which is a step the model could have taken itself, since it computes that query when asked.

\begin{figure}[t]
\centering\includegraphics[width=\columnwidth]{col_conventions.pdf}
\caption{Main answer to the open request on 61 tie and counting sets: the reading BIRD and Spider references take by convention, the other reading, or neither.}
\Description{Stacked horizontal bars per model; the conventional reading outnumbers the other reading by about four to one for every model.}
\label{fig:conventions}
\end{figure}

\textbf{Silent choices follow benchmark conventions.}\label{sec:filterresults} When a model settles a choice without saying so, it takes the reading that benchmark authors take. In 61 tie and counting sets, one reading is the convention of BIRD and Spider references (Section~\ref{sec:defaults}): a plain \sql{LIMIT} rather than every row tied at the cut-off, and counting joined rows rather than distinct entities. The conventional reading is the intended one in 29 of these sets, so the design favours neither. Yet when a model's main answer is one of the two readings, it is the conventional one in 80--87\% of cases for every model (Figure~\ref{fig:conventions}). The conventional reading is also the simpler SQL, so these data cannot separate habit from simplicity. Either way, models settle an open choice the way benchmark authors do, which is also the reading that a benchmark built by those authors rewards.

\textbf{The same holds on AMBROSIA.} The pattern is not an artifact of our tests. AMBROSIA pairs each ambiguous question with one unambiguous question per reading, and Saparina and Lapata~\cite{saparina2025disambiguate} observe that models usually give one preferred reading. We split each missed reading into one the model cannot compute and one it computes but does not report. On 120 ambiguous test questions per model, the model computes 49--66\% of the readings it misses when asked the unambiguous version (Figure~\ref{fig:decomposition}). Even when a model answers every unambiguous version correctly, it returns all readings for the ambiguous question in only 7--28\% of questions. On the 40 vagueness questions per model, which ask which column or value a phrase means, models compute 48--56\% of the readings they miss, so the gap also covers the referent-column choices that our request sets leave out. On both benchmarks, models compute what is asked and stay quiet about settled choices, but leave open choices unreported, whatever the source of the ambiguity.

\textbf{Examples.}\label{sec:examples} For the film request of Figure~\ref{fig:teaser}, GPT-Sol states reading A, which matches its SQL, but treats the choice as settled; GPT-Luna says the choice is open but gives no second query; Sonnet adds B: ``per-day price defined as the rating's average rental\_rate divided by its average rental\_duration (ratio of averages).'' Responses can also mislead in the other direction. For a specific request on fees, Haiku computes a mean of channel means, which matches the other reading and contradicts the request; for an open count of awards, Sonnet names the choice and gives both \sql{COUNT(*)} and \sql{COUNT(DISTINCT player\_id)}.


\section{Benchmarks Cannot See the Gap}
\label{sec:diagnosis}
BIRD and Spider score a model against one reading even where a question leaves the choice open, and which reading they take depends on who wrote the question. On held-out questions, the four models answer 49--74\% of BIRD questions correctly as worded but 96--100\% from the exact description of the reference SQL (Figure~\ref{fig:real}). Allowing extra or reordered output columns closes only part of this gap, and on Spider the remaining gap is smaller.

\begin{figure}[t]
\centering\includegraphics[width=\columnwidth]{col_real.pdf}

\Description{Grouped bars for four models on BIRD and Spider held-out questions under three conditions.}

The exact description gives the reference's steps, columns and choices at once, so this gap bounds what the wording costs rather than measuring ambiguity alone. To see what it consists of, a reviewer model assigns one cause to each development question answered correctly from the description and wrongly as worded (Figure~\ref{fig:causes}). Output columns, a phrase mapped to another column or value, unstated requirements and run-to-run variation cause most failures. Output columns are a matter of form: the answer holds the right values in a different shape, such as a name instead of an ID. Open choices cause 6\% of BIRD and 14\% of Spider failures. These open choices are the ones our library collects.




 Other choices are about which column a word means: for ``Name schools in Riverside\ldots'', filtering the district field returns six rows, the county field sixty and the city field seven. Code cannot tell from a reference which column the question's word could also mean, so request sets do not test this type; AMBROSIA's vagueness questions cover it.

\subsection{References follow unstated conventions}
\label{sec:defaults}
When a question is silent on a choice, its reference still takes one reading, and the reading depends on the author group. We read seven such choices off reference SQL, among them ties at an extreme, counting over a join, join type, and whether ``between'' includes its bounds. On five of the seven, every author group takes the same reading in at least 91\% of silent questions. On ties and counting, the groups disagree (Figure~\ref{fig:defaults}). Asked for an extreme value, BIRD and Spider references return one row in over 90\% of silent questions, but the Geo and Restaurants questions that Spider imported from older datasets return one row in 21 of 247. Asked for a count over a join, BIRD references count joined rows in most silent questions, and the imported Academic, IMDB and Yelp questions in none of 39. Each group keeps its convention in training and development data alike, so examples retrieved from a benchmark's training data can carry its authors' convention into a model's answers. For the same wording, a model that follows BIRD's convention is therefore scored right on BIRD and wrong on the imported Spider questions: the score measures agreement with the authors, not correctness.

\subsection{The unstated reading changes answers}
The choice a reference makes silently is not cosmetic. For each BIRD development question that is silent on a choice, we apply the library's edit for the other reading to the reference SQL wherever it gives a valid reading, and run both. Of 664 such questions, 156 (23\%) change their answer (Figure~\ref{fig:impact}). Counting matters most, often by more than half of the value. For ``How many accounts in North Bohemia has made a transaction with the partner's bank being AB?'', the reference counts joined rows and returns 2,260, while counting each account once returns 55. Ties change about a quarter of answers, often the list of returned items, and join type and missing-value filters change about one in ten. The data behind these choices are common: every one of the 12 evaluation databases has at least two kinds of data on which an unstated choice changes an answer, such as joins that repeat rows, columns with missing values and maxima shared by several rows.

\textbf{BIRD scores the other reading as wrong.} A model that takes the unstated reading of a silent question loses accuracy for an answer the question allows. We ask the four models 137 BIRD development questions on which a tie, counting or join edit of the reference changes the answer, and score each answer against both queries. An author reviewed every question on which an answer matched only the edited query; the edits rejected removed DISTINCT, edited one side of a ratio, or turned a join that acts as a condition into an optional one, and a rule that excludes these three reproduces all 39 verdicts. Of the 233 answers BIRD marks wrong on the 79 questions the rule keeps, 102 return the other reading. On tie and counting questions, more answers match the edited reference (94) than the reference itself (37), and on 18 questions every model returns the other reading (Table~\ref{tab:answers}). Accepting both readings raises accuracy on these questions from 26\% to 59\%.

\section{Two Design Rules for Reliable Answers}
\label{sec:method}
Models usually compute a missed reading once it is asked for on its own (Section~\ref{sec:disclosure}). A system can therefore ask for each reading separately and let execution decide which readings differ. This section tests two rules built on this observation: show an alternative only when its result differs (Sections~\ref{sec:methoddesign}--\ref{sec:methodambrosia}), and carry a clarification by adding one clause to the request rather than rewriting it (Section~\ref{sec:rewrite}).



\subsection{Method}
\label{sec:methoddesign}
The method asks once for the readings of a request and answers each in its own call (Figure~\ref{fig:methodsteps}). One call lists the readings, each rewritten as a request with exactly one reading. If there is only one, one more call answers it and nothing else runs. Otherwise all answers are executed, readings with identical results are merged, and the first is returned with the others as alternatives. Whether two readings differ depends on the data, so execution can show that readings differ but not that they are equivalent~\cite{testsuite2020}: a merged choice may matter on other data.

\caption{The disclosure method on the film request (an illustration). Blue and orange: readings A and B, as in Figure~\ref{fig:teaser}.}
\Description{Four steps: list the readings, answer each in its own call, run both and compare the results, show one answer with the choice and the other reading.}
\label{fig:methodsteps}
\end{figure}

\subsection{Show an alternative only when its result differs}
\label{sec:methodambrosia}
\label{sec:exchange}
We developed the method on 60 AMBROSIA questions and then froze it. A variant that lists the readings twice was dropped by a rule fixed in advance, because it lowered precision by more than two points. Two criteria were also fixed before the final test: higher precision on unambiguous questions than DtP, and AllFound within ten points of it. The final test uses 150 new test questions per model (90 ambiguous, 60 unambiguous) and compares four methods, run interleaved with the same model: the authors' prompt (plain); DtP with its released prompts, its fine-tuned infilling step replaced by that step's prompt; the authors' prompt sampled three times, at about our cost (three samples); and our method.

Our method is the most precise (Figure~\ref{fig:method}). Pooled over both models, it is 19.2 points more precise than DtP ($[12.3, 26.1]$) at about a third of DtP's calls, because it shows an alternative only when its result differs. DtP is even less precise than plain, because it adds readings to clear questions. The coverage criterion fails: DtP returns every reading for more ambiguous questions, by 8.3 points pooled, mainly with GPT-Sol, which lists more readings under DtP.

\subsection{Edit the request, do not rewrite it}
\label{sec:rewrite}
Many systems rewrite a request before the SQL step. Retrieval chat frameworks such as LangChain's ConversationalRetrievalChain~\cite{langchain2024crc} and LlamaIndex's CondenseQuestionChatEngine~\cite{llamaindex2024condense} condense each follow-up into a standalone question. Snowflake's text-to-SQL service, Cortex Analyst, rewrites each question into a self-contained one before it writes SQL~\cite{xu2024cortex}, conversational text-to-SQL parsers are trained to make the same rewrite~\cite{xiao2022cqrsql,chai2023qurg}, and DtP writes each reading as a short interpretation. Each rewrite is a new copy that can lose a requirement. Figure~\ref{fig:rewriteex} shows a rewrite on the financial database that dropped the region, the region share and the top-ten cut, while the request with one added clause was answered right.

\begin{figure}[t]

\caption{What a rewrite loses: one request set reading on the financial database.}
\Description{The original request with three lost requirements marked, its rewrite, and the request kept with one clause.}
\label{fig:rewriteex}
\end{figure}


Our request sets follow the opposite rule, since the three requests differ only in the choice, so we test which rule a clarification should follow. For each reading of a request set, the same SQL prompt receives one of four texts: (a) the original specific request; (b) the open request rewritten by the model as one interpretation with DtP's prompt, told the intended reading; (c) the open request unchanged, followed by a one-sentence description of the reading; (d) the open request condensed by the model into a standalone question with LangChain's condense-question prompt~\cite{langchain2024crc}, with the open request as the earlier turn and the reading as the follow-up. Texts (b) to (d) start from the same open request and the same description. We report the 363 readings from accepted sets.

\begin{figure}[t]

\label{fig:rewrite}

Keeping the request and adding one clause computes 85.4\% of the readings correctly, as many as the original specific requests (Figure~\ref{fig:rewrite}). Both rewrites compute fewer: 6.9 points fewer for the interpretation rewrite and 11.6 for the standalone question, and the loss is largest for Haiku and GPT-Luna. The rewrite seldom loses the choice itself. Of the readings answered correctly from the original request and wrongly from the rewrite, the judge finds the choice lost in only 6\%; the rest lose another requirement, most often an output column, a formula or a join (Figure~\ref{fig:rewrite}, right). On \texttt{insider}, Sonnet's rewrite turned ``its average minus the baseline'' into ``its deviation from it'', and the SQL took the absolute deviation; on Formula~1, Haiku's rewrite dropped ``one row'', and the SQL returned one row per race name instead of one row.



\textbf{The same holds on real questions.} We repeat the comparison on 85 BIRD development questions where one library edit of the reference SQL changes the answer. A simulated user follows each question with one sentence that settles the choice, such as ``If several rows tie at the cut-off, return all of them,'' and the edited reference is the gold answer. Over 170 question--model pairs with Sonnet and GPT-Sol, adding the clause beats the standalone question, 58.2\% against 47.6\%. As on our request sets, the rewrite keeps the clarified choice and loses something else; the gap is largest for ties. Our method's first call also rewrites the request per reading and can inherit this loss, as can retrieval chat, planners and hand-offs between agents.

\section{Implications}
\label{sec:lessons}
\textbf{Systems could check readings on the user's data.} Our results suggest that a model states its reading accurately and can usually compute the other one, yet seldom reports it. A system may therefore not need a stronger model to report open choices; a step that asks for each reading, executes the answers, and shows an alternative only when the results differ can already help. The data, not the wording alone, decide whether a choice matters: the two readings of the film request differ on \texttt{sakila\_1} for every rating, but on a table where every film rents for the same number of days they return the same answer. The check is worth repeating when the data change, since one update can make a choice matter. When the user then settles the choice, keeping the original request and adding one clause appears safer than a rewrite, which can drop a column, a formula or a join that the user asked for.

\textbf{Reporting could be a training target.} The models we test already compute both readings of most requests; what they mostly lack is the habit of reporting the second one. This points to training rather than scale as a promising direction: Sonnet, the strongest model, still misses the other reading in four of ten sets where it can compute it. Request sets could supply the signal such training needs. Each reading has its own executable reference, so a reward can credit an open answer only when it returns both readings and charge a specific answer for every alternative it adds. Because the two specific requests differ from the open one only in the choice, such a reward would separate reporting from computing.

\textbf{Benchmarks could reward stating assumptions.} Current benchmarks score a single answer per question, which suits questions with one correct reading. For a question that is silent on a choice, a complementary practice is to let the model state the assumption it made and the alternative it set aside, and to credit both when each matches its own reference. This mirrors how analysts work: a colleague who answers an open question usually says which reading they took, so the user can check the answer without reading the SQL. Request sets make this possible: each reading has its own reference, so a benchmark can report accuracy on specific requests, disclosure on open requests, and restraint on settled ones, where restraint keeps a model from earning disclosure by raising a choice on every request. Adoption could start small. The library's SQL edit produces the second reference query from the first, as Section~\ref{sec:defaults} does for BIRD, and could be accepted as a second answer wherever a question is silent on the choice, beginning with counting units and ties. Request sets can also be built on a benchmark's own databases at little cost: a new database needs one model review of its column meanings, and a new choice type one SQL edit that then applies to every database.

\section{Related Work}
\label{sec:related}
\textbf{Natural language interfaces to databases.} NaLIR~\cite{nalir2014} fixed ``easy'' ambiguities quietly and, for each ``hard'' one, explained its interpretation and offered several for the user to choose from. Its ambiguities lie mainly in mapping words to schema elements and in how phrases attach. Current models make these mappings well, but they return SQL without showing their reading. Our results show that the alternatives NaLIR asked users to choose among are now cheap to compute; what is missing is the report. Our method applies NaLIR's interaction to calculation choices and lets execution decide which choices are ``hard'': only readings with different results are shown, and a choice that changes nothing stays hidden.

\textbf{Evaluation.} Spider tests generalization across schemas~\cite{spider2018}; BIRD adds large databases and external knowledge~\cite{bird2023}; KaggleDBQA uses realistic databases and documentation~\cite{kaggledbqa2021}; Spider 2.0 tests enterprise workflows~\cite{spider22025}. SParC and CoSQL add context and dialogue~\cite{sparc2019,cosql2019}, and BIRD-INTERACT tests clarification and recovery~\cite{birdinteract2026}: it scores whether a system completes a task after asking the user, whereas request sets score whether it reports a choice it made without asking. TrustSQL rewards a model for abstaining when it cannot answer reliably and penalizes wrong answers~\cite{lee2024trustsql}; request sets reward a different behaviour, answering while reporting the open choice. Test suites~\cite{testsuite2020} showed that execution on one database accepts wrong queries whose results match by chance, and distill databases that separate them from the gold query. Our concern is the opposite error: a correct query for another valid reading is rejected because the reference fixes one reading. Both rest on the fact that whether two queries differ depends on the data. Pourreza and Rafiei re-evaluated top models on Spider and BIRD by hand and found a perfect score out of reach ``due to the multiple interpretations that can be derived from the provided samples''~\cite{pourreza2023evaluating}, and Wretblad et al.\ found noise in BIRD's questions and references whose correction changed which method ranks first~\cite{wretblad2024noise}. We measure the first problem by construction rather than inspection and keep possible reference errors apart from open choices, because a wrong reference and a valid but different one need different fixes.

\textbf{Ambiguous requests.} The closest benchmarks are AmbiQT~\cite{ambiqt2023} and AMBROSIA~\cite{ambrosia2024} (Table~\ref{tab:comparison}). AmbiQT makes Spider questions ambiguous by changing the schema, with synonym columns or tables, split tables and precomputed aggregates, and checks whether both gold queries appear in the top five outputs. AMBROSIA has human-written questions with scope, attachment and vagueness ambiguity on generated databases. Both locate ambiguity in the schema or the wording. The choices behind the benchmark conventions of Section~\ref{sec:defaults}, such as ties, counting units, missing values and aggregation level, lie in the calculation and fall outside both taxonomies. For code generation, Menet et al.~\cite{menet2026tdd} model generation from execution feedback as Thompson sampling and prove a regret bound with an irreducible term set by the ambiguity of the task description. Request sets measure this term in SQL, as the gap between the open and the specific requests, and our method addresses it by disclosure to the user rather than by more rounds of feedback, which cannot remove what the wording leaves open.

\textbf{Generation, SQL methods and semantic layers.} DBPal~\cite{dbpal2020} and GAZP~\cite{gazp2020} generate training pairs for a target database; DBPal fills seed templates from the schema and adds automatic paraphrases. We also start from the database, but for evaluation: a request set fixes the database and every requirement but one, and execution checks that the change alters the answer. RAT-SQL, PICARD, DIN-SQL, DAIL-SQL, CHASE-SQL and Alpha-SQL~\cite{ratsql2020,picard2021,dinsql2023,dailsql2024,chasesql2025,alphasql2025} improve how the SQL is generated. Methods that retrieve training examples, such as DAIL-SQL, can carry the benchmark authors' conventions into the answers, so part of a benchmark gain may come from matching them. LookML has developers write each measure ``once, in one place''~\cite{lookml2025}, the dbt Semantic Layer centralizes metric definitions~\cite{dbtsl2025}, and Cortex Analyst generates SQL from them~\cite{cortexdocs2025}. A layer settles the choices its authors foresaw, usually a measure's formula and counting unit; per-request choices, such as ties at a cut-off or the rows a ratio includes, remain open.

\section{Conclusion}
\label{sec:discussion}
Text-to-SQL models make choices without saying so. Request sets, which change only one calculation choice, make this visible: four models compute both readings of most sets when each is asked for, yet return both for the open request in only 16--58\% of those sets, and most missed readings come without a mention of the choice. When they settle a choice silently, they take the reading that benchmark references take by convention. Benchmarks cannot see the gap, because their references take one reading by conventions that differ by author group, and on BIRD nearly one in four questions silent on a choice changes its answer under the other reading; over two in five answers BIRD marks wrong there give that reading. Two design rules make answers more reliable: show an alternative only when its result differs, and clarify a request by adding one clause. The models already hold the other reading; what is missing is a step that shows it, and a benchmark that asks for it.

\textbf{Limitations and future work.} The generator covers a subset of analytical SQL, and the library comes from two benchmarks on SQLite, so other benchmarks may hold choice types we have not seen. The request sets cover every choice type on which real references differ, except two: quantifier, which the generator does not yet build, and referent column, which code cannot read off a reference; for the latter, AMBROSIA's vagueness questions show the same gap. Models write the request sets and judge the explanations, but an author reviewed every set, and execution decides every accuracy and coverage number. The judge that decides naming does not know which model answered, and a stated reading matches the SQL in nearly every response, so the judge has little room to err in one direction. A second writer of the natural requests shows no home advantage. One author accepted the sets, without model results; the conventions are read by rules that see one SQL form each, so their counts are lower bounds. The BIRD rescoring uses one call per question without exploration, so its shares may shift with stronger prompting. We measure what a system shows, not how analysts decide with it. A system that can ask the user, as in BIRD-INTERACT, may settle a choice before it answers; request sets can measure whether it asks only when a choice is open. Other SQL dialects, multi-turn sessions and a user study of how analysts act on a reported choice are the next settings to test.
