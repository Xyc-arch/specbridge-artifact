\begin{abstract}
A text-to-SQL answer can run, return a plausible number and still compute something other than what the analyst meant. This can happen when the request leaves a calculation choice open, such as whether to count rows or distinct entities, and the model settles it without saying so. Standard benchmarks cannot detect this, because they score each question against a single reference interpretation. We introduce \system{}, which tests such a choice by varying it alone: it poses three otherwise identical requests, one leaving the choice open and one per interpretation, and scores each answer by running it. The databases are real, and the choices are ones that made models fail on existing benchmarks. On 204 hand-validated tests, four language models usually compute each interpretation when asked for it, yet for the open request return both in only 15--58\% of the tests where they can, often without mentioning the choice. The gap lies in reporting, not in computing. Benchmarks even penalize the alternative: on BIRD questions where such a choice changes the answer, over two in five of the answers marked wrong are right under the other interpretation. Because the models can compute what they miss, a system can narrow the gap without a stronger model: it first decides whether a request leaves a choice open, then answers each interpretation in its own call. On our tests and on AMBROSIA, an existing benchmark of ambiguous questions, this approach raises the share of open requests that get every interpretation by 29--63 points over the single answer that production assistants give, without lowering precision on clear requests. It also needs fewer user turns than asking a clarifying question.
\end{abstract}

\section{Introduction}
\label{sec:intro}
Analysts increasingly ask for numbers in natural language and get them from a text-to-SQL system, often without reading the SQL. For these users a query that fails is safe, because the error is visible. The dangerous case is a query that runs and returns a plausible number, computed differently than the analyst meant. Small choices in how a number is computed can change a published finding. An influential study reported that high public debt slows growth. It first averaged growth within each country, then across countries, so a country with one high-debt year counted as much as a country with many. With corrected data and each year counted equally, high-debt countries grew 2.2\% a year, not $-0.1\%$~\cite{herndon2014debt}. Table~\extref{tab:cases} lists more cases across six domains. A text-to-SQL system makes such choices on many requests, and the result alone does not show them. We call such a choice, settled without telling the user, a silent choice. The answer is correct for one interpretation, so checks that look for wrong SQL~\cite{chen2023error,alrashed2026verification} do not catch it.

Take ``the average rental price per day'' for each film rating (Figure~\ref{fig:teaser}). It can be computed in two ways, which we call interpretations. Interpretation A averages each film's daily price, and interpretation B divides the average price by the average rental duration. For two films priced at \$6 for two days and \$6 for six days, A gives $(\$3 + \$1)/2 = \$2.00$ per day and B gives $\$6/4 = \$1.50$. Both are simple SQL, and on Spider's \texttt{sakila\_1} database the two interpretations differ for every rating. We test four models: Claude Haiku~4.5, Claude Sonnet~5.5, GPT-6 Sol and GPT-6 Luna (Haiku, Sonnet, GPT-Sol and GPT-Luna below). For the request as worded, which leaves this choice open, all four return A. Sonnet and GPT-Luna say that there is a choice, but only Sonnet also gives B, the ratio of two averages.

A reliable text-to-SQL system must do three things: \req{1}~compute the interpretation that a specific request asks for, \req{2}~report a choice that a request leaves open together with the other interpretation, and \req{3}~stay quiet about a choice that the wording already settles. Production assistants handle open choices by stopping. Snowflake's Cortex Analyst rejects a question its classifier marks ambiguous~\cite{sehrawat2024cortex}, Databricks' Genie asks a clarifying question where its authors' instructions say so~\cite{genie2025}, and Microsoft's Fabric data agent leaves it to instructions its authors write~\cite{fabric2026agent}. When these assistants do answer, they return one interpretation and state it~\cite{cortexrest2025}. By default, none of them meets \req{2}.

Benchmarks measure \req{1}--\req{3} only in part. Spider and BIRD measure only \req{1}. They score each question against one reference, even when the question leaves a choice open. A model that guesses the authors' interpretation thus scores as well as one that reports the choice. Ambiguity benchmarks~\cite{ambiqt2023,ambrosia2024} add \req{2}, and AMBROSIA also adds \req{3}. Three gaps remain (Table~\ref{tab:comparison}). First, both create their choices: AmbiQT edits Spider's schemas, and AMBROSIA generates synthetic databases. These choices lie in the schema or the wording, such as which column a word means. Choices in how a number is computed, as in the debt study, are not among them. Yet such choices arise naturally in BIRD and Spider questions, and the references settle them by convention. Second, both score only the SQL a model returns. A user who does not read SQL learns of a choice only if the model says so. Third, their scores do not show why a model misses an interpretation. The model may be unable to compute it, or it may compute it but not report it. The first calls for a stronger model; the second does not.

Our key idea is a controlled test: three requests that differ in the choice and in nothing else. Two are specific, one asking for interpretation A and one for B. The third, the open request, leaves the choice open. With the two reference queries, the three requests form a request set (Figure~\ref{fig:teaser}). All three use the same prompt. It asks the model to state any assumption that the request does not settle and to give SQL for other interpretations. We score the SQL by execution and the explanation by a judge model. Because nothing else differs, each failure has one cause. A wrong answer to a specific request is a failure to compute (\req{1}). On the open request, missing an interpretation that the model computes when asked for it alone is a failure to report (\req{2}). Raising the choice on a specific request is a false alarm (\req{3}), because its wording settles the choice.

Building request sets at scale is hard for three reasons. First, a test must control what each query computes and describe it exactly, on databases that nobody has annotated. Second, the choices must be ones that matter in real requests, not invented ambiguities. Third, the three requests must differ only in the choice, yet a rewritten request easily changes other requirements. \system{} addresses each in turn. It generates SQL from a catalogue of column meanings, and code describes each query exactly in words (Section~\ref{sec:construction}). It mines choices from BIRD and Spider questions that models fail as worded but answer correctly from an exact description of the reference SQL (Section~\ref{sec:library}). It applies a choice to a query only if the choice changes the answer. It writes the three requests from one list of shared requirements, and code and two reviewer models check every set (Section~\ref{sec:apply}). Two authors then cross-checked all 307 passing sets without seeing model results and kept 232 (76\%), so no result rests on model reviewers alone. Results use the 204 of them on choice types where real references differ (Section~\ref{sec:specresults}). Execution, not a model, decides every accuracy score in this paper.

\textbf{Finding 1: Models make choices without saying so} (Section~\ref{sec:disclosure}). On 204 accepted request sets (Figure~\ref{fig:disclosure}), the models compute what is asked (\req{1}) and stay quiet about settled choices (\req{3}), but leave open choices unreported (\req{2}). They answer both specific requests correctly in most sets and almost never call a settled choice open. Yet for the open request, they return both interpretations in only 15--58\% of the sets they can compute, and they name the choice in only 38--70\% of all sets. Accuracy hardly separates the models, but reporting does. Even the larger model of each family does not close the gap. Saparina and Lapata~\cite{saparina2025disambiguate} observed that models usually give one preferred interpretation of an ambiguous question. Request sets show that they can usually compute the others. In 72--94\% of the sets where a model misses an interpretation, the same model computes it correctly when asked for it alone. Most misses are thus failures to report, not failures to compute. AMBROSIA's paired unambiguous questions allow the same split, and there models compute 49--66\% of the interpretations they miss.

\textbf{Finding 2: Benchmarks cannot see the gap} (Section~\ref{sec:diagnosis}). When a BIRD or Spider question leaves a choice open, its reference SQL still takes one interpretation, by a convention of its author group. BIRD's and Spider's own authors return one row when several rows tie, and count joined rows rather than distinct entities. The question groups that Spider imported from older datasets each reverse one of these two conventions. The choice is not cosmetic. On BIRD, 156 development questions change their answer under the other interpretation: nearly one in four of those that leave a choice open, and one in ten of all. On 79 such questions, two authors confirmed that the other interpretation is valid. Over two in five of the answers that BIRD marks wrong on them give that interpretation. Accepting both interpretations raises the four models' accuracy from 25\% to 57\%. For these questions, a benchmark score measures agreement with the benchmark's authors, not correctness, and cannot show whether a model reports the choice.

\textbf{Finding 3: Deciding first makes reporting more reliable} (Section~\ref{sec:method}). Because models can compute what they miss, a method can narrow the gap without a stronger model. Asking and reporting both start by noticing that a choice exists, but asking costs the user a round trip on every flagged request. Phase 1 of our method, \method{Decide-then-answer}, therefore first decides whether a request leaves a choice open. It then answers each interpretation of an open request in its own call and lets execution decide what the user sees. Against \method{Single answer}, the one answer that production assistants return, it returns every interpretation for 28.9 points more of AMBROSIA's ambiguous questions and 63.1 points more of the open requests in request sets. It loses no precision and makes 2.5 to 3.1 calls per request. In a simulated two-turn conversation, it needs 35.0 to 40.8 fewer user turns per 100 requests than \method{Clarifying question}. It is also more precise than two prompting baselines and \method{DtP}~\cite{saparina2025disambiguate}, by 5.9 to 52.0 points. \method{DtP} also answers each interpretation, but it has no step that spots clear requests, and it returns every interpretation more often only on AMBROSIA. Phase 2 keeps the request and adds the user's pick as one clause. This beats rewriting the request with \method{DtP}'s or LangChain's prompts by 8.5 to 10.5 points of correct answers on request sets.

In summary, we make three contributions: (1) request sets, controlled tests that change one calculation choice and are scored by execution, with a generator that builds them on real databases and a library of choices mined from benchmark failures (Sections~\ref{sec:framework}--\ref{sec:evaluation}); (2) findings on four models across our request sets, AMBROSIA and BIRD (Sections~\ref{sec:disclosure}--\ref{sec:diagnosis}); and (3) a two-phase method that reports open choices and carries the user's pick, tested against prompting, sampling, \method{DtP} and production behavior rebuilt from documentation (Section~\ref{sec:method}). We release the generator, the 307 request sets with the authors' verdicts, all model responses, and a package that reproduces every number in this paper without new model calls; a supplement shows how common each choice type is, with examples, and gives the generator's details and the data behind each experiment, so every figure and table can be traced to its data file.
\section{\system{} Overview}
\label{sec:framework}
\system{} is named for its central step, which bridges an exact specification of each query, written by code, and the natural requests a user would write. It turns a database into request sets in two lanes that meet in one step (Figure~\ref{fig:pipeline}). The first lane generates queries whose computation is known exactly. The second lane mines, from benchmark failures, the choices that real requests leave open. The last step applies one such choice to a generated query and writes the three requests. We first follow two request sets through this process (Section~\ref{sec:worked}) and then describe the steps of generating queries (Section~\ref{sec:construction}), mining choices (Section~\ref{sec:library}), and building and checking request sets (Section~\ref{sec:apply}), the step that keeps the three requests aligned on everything but the one choice.

\subsection{Two examples}
\label{sec:worked}
\label{sec:test}
A request set fixes a database and every requirement of a query but one choice. The film request of Figure~\ref{fig:teaser} asks for each rating's average replacement cost and daily rental price, and compares that daily price with the average across ratings. Only the daily price is open:
\begin{equation}
 A=\operatorname{AVG}(\text{price}/\text{days}),\qquad
 B=\frac{\operatorname{AVG}(\text{price})}{\operatorname{AVG}(\text{days})}.
\end{equation}
A averages each film's daily price; B divides two averages and so gives more weight to longer rentals. The specific request for A asks for the average of per-film daily prices, the one for B asks for the average price divided by the average duration, and the open request asks for the ``average rental price per day.'' The rest of the wording is shared, and code checks that the two queries return different results on the database; a choice that does not change the answer is not tested there. \label{sec:additionalexample}The second example (Figure~\ref{fig:worked}) is a three-step query on the \texttt{insider} database. It averages short-interest measurements for each transaction, compares each transaction with a baseline for its order type, and returns the ten largest ratios. The choice lies in the baseline. Interpretation A averages the transaction means, so each transaction counts once, while B averages the underlying snapshots, so a transaction with more snapshots weighs more. The open request asks for ``the average short interest for its order type mix,'' and all ten output rows change between the interpretations.

\subsection{Generating queries}
\label{sec:construction}
\label{sec:querygen}
\label{sec:writing}
Generation starts from the database, not from a benchmark, so it works on databases nobody has annotated. One model review of the schema and data first builds a catalogue of column meanings, units and table relationships; after that, generation calls no model. A query starts from counts, sums or averages per entity, per group or overall. Later steps can compare a value with a broader average, take a share of a total, combine compatible quantities, aggregate again, or keep the top entities per group. We control two properties of each query, its arithmetic depth (the nesting of arithmetic expressions) and its step depth (the number of dependent query stages). Rules on column types decide which quantities can be combined or summed, and data checks reject empty answers, constant or redundant quantities, non-positive denominators and too-small groups. The generator looks ahead and drops a partial query as soon as it can no longer reach the requested depths, so no attempt is spent on a dead end, and every delivered query has exactly the arithmetic and step depths it was asked for.

Code then describes each query exactly in words. The text covers source rows, joins, unmatched rows, filters, groups, formulas, missing values, ordering, limits, ties and SQLite conventions, and the same SQL always gives the same text; we call it the exact description. Because the exact description states every requirement, a model that fails from it cannot compute the query, while a model that succeeds from it but fails from a natural request was misled by the wording. Section~\ref{sec:library} builds on this contrast. Sonnet turns the exact description into one natural request using the column meanings. Claude Opus~5.5 (Opus below) checks the request for missing, changed or added requirements, and code checks how stored values are written. A failing request gets one revision with the reviewer's notes and is dropped if it fails again.

\subsection{Mining choices from benchmark failures}
\label{sec:library}
The choices come from real benchmark failures. For each BIRD and Spider question, we compare a model's answer to the original question (with BIRD's evidence) with its answer to the exact description of the reference SQL. When only the description is answered correctly, the wording caused the failure, not the model's SQL, and we classify the reason as output columns, a different column or value, an unstated requirement, numerical precision, or an open choice. For an open choice, the other interpretation is written as an edit of the reference SQL, and both queries are executed. Opus and Sonnet judge each interpretation independently, and disagreements are kept. The library keeps choices of meaning, both open ones, where the wording fits both interpretations, and settled ones, where it selects one. For ``What is the total number of molecules with double bonded oxygen?'', both reviewers accept only the interpretation in which the oxygen atom is part of the double bond, although the reference SQL counts every molecule that contains an oxygen atom and a double bond. Figure~\ref{fig:choices} groups the library by choice type. The largest group of open choices concerns which column a phrase refers to, and half of the settled ones concern the counting unit.

The same choices appear in benchmark references, and the references do not agree on them. We say that a question leaves a choice open, or is open, when neither its wording nor BIRD's evidence contains a word that settles it, such as ``all'' for ties or ``distinct'' for counts. For 12 of the 13 choice types, code reads which interpretation a reference takes, and Figure~\ref{fig:choices} counts the open BIRD and Spider questions and the share whose reference takes the rarer interpretation. Every case of the rarer interpretation was reviewed and only confirmed cases are counted, so these shares are conservative. For example, 12.3\% of open tie questions return every tied row, and 8.6\% of open questions that count over a join count distinct entities. Here a benchmark that scores one interpretation treats a convention as the only answer.



\subsection{Building request sets}
\label{sec:apply}
\label{sec:filters}
A request set needs a choice that matters on the data, so code first reports where a generated task's columns have missing values, repeated join matches, distinct values or ties. Opus proposes one choice from the library and an exact SQL edit for it, and code checks that the edit applies, runs, changes the answer and can still be described exactly; a failed proposal gets one repair. Opus then writes the request set from a plan that lists the shared requirements and the one differing choice. It writes the request for A, edits it for B, and writes the open request. A library example of the same type may guide the wording, but never supplies the SQL. Opus and Sonnet, as two reviewers, check that the requests keep their requirements and judge each of the three requests against each interpretation. A set is kept only when both reviewers accept each specific request for its own interpretation alone and at least one accepts the open request for both interpretations. Five library types concern a filter, such as whether a cutoff is strict. Generated queries seldom filter, so for these types the generator adds one condition chosen from the data. Figure~\ref{fig:choices} gives an example of each type. The pipeline keeps 307 request sets on 12 databases, and 204 of them pass the authors' review and a check against real references (Section~\ref{sec:specresults}).

\section{Measures}
\label{sec:metrics}
We score what a model computes by execution and what it says by a model judge. We report four measures: accuracy for \req{1}, both returned and named for \req{2}, and false alarms for \req{3}. A specific request selects one interpretation, and the open request fits both. A choice is settled when the wording selects one interpretation. We execute every returned query and compare its result with the reference result, with numerical tolerance and with rows tied at a cut-off treated as interchangeable; an execution error scores zero, as in Spider and BIRD scoring. For benchmark questions we also report a score that allows extra or reordered output columns.

For the open request, the model returns a main query and up to two alternatives. The model returns both interpretations when these queries include one with the result of A and one with the result of B. We report this share over all sets and over the sets in which the same model answers both specific requests correctly, where a miss cannot be a failure to compute. Written as a formula, with $S_i$ the queries returned for the open request of set $i$, $e(p,\hat p)=1$ when query $\hat p$ returns the result of reference $p$, and $B_i=1$ when both specific requests are answered correctly,
\begin{equation}
\mathrm{Both}=\frac{\sum_i B_i\prod_{j\in\{A,B\}}\max_{\hat p\in S_i}e(p_j,\hat p)}{\sum_i B_i}.
\end{equation} A missed interpretation is computable when the same model answers the specific request for it correctly. A model names the choice when its explanation says that the choice is open, whether or not it gives SQL for the other interpretation. A judge model, which does not know which model answered, decides whether a response names the choice and whether its stated interpretation matches its SQL. For a specific request, offering the other interpretation, or calling the choice open, is a false alarm; an alternative on another choice, which the set does not test, is not. The measures check one another. Returning both interpretations alone would reward a model that adds every alternative it can think of, and the false alarms charge for that; naming alone would reward a warning without an answer, and returning both interpretations charges for the missing query. Table~\ref{tab:scoring} scores four recorded responses.

\textbf{Why every score is exact.} Each request is written from the exact description of its query, so a specific request states every step, the choice included, and has exactly one correct result: an answer is right if and only if it returns the reference result. The open request leaves out only the choice phrase. Its two interpretations come from practice, not from us: real BIRD and Spider references take each of them on open questions, and we keep only choice types for which at least 1\% of references take the less common one (Section~\ref{sec:specresults}). We therefore measure precision, the share of returned queries with the one correct result, only on specific requests, and on the open request we ask only whether both A and B are returned, never counting other answers against the model. A choice might admit a further interpretation; we do not score it, and it could only lower the true share of open requests answered with every interpretation, so the gaps we report are conservative.

On AMBROSIA, each ambiguous question comes with two or more interpretations (three for 30 of the 90 we test), and an interpretation is found when some returned query gives its result. Recall is the share of interpretations found, and AllFound is the share of questions with every interpretation found~\cite{ambrosia2024}. Precision on an unambiguous question is the share of returned queries with its one correct result, so extras lower it.

\subsection{Checks on the tests}
\label{sec:specresults}
\label{sec:resconstruction}
\label{sec:writerswap}
The findings rest on tests that change only the choice, so we check the tests first (Figure~\ref{fig:funnel}). Code confirms that in each of the 307 sets that pass all checks, the two queries differ in one step and the two specific requests differ only in the choice phrase. Two authors then cross-checked every set without seeing model results and kept it only if a reasonable analyst could mean either interpretation. They keep 232 of the 307 sets (76\%). Most rejected sets have an open request whose wording already favors one interpretation, or a choice that convention settles, such as ``between,'' which includes both ends in SQL and in almost every benchmark reference. We also keep only the choice types on which real references differ (Figure~\ref{fig:choices}), which leaves 204 sets on aggregation level, cutoffs, ties, counting units, missing values and one negation. Every result below uses these 204 sets. The review does not drive the results. With no human filter, models return both interpretations in only 11--48\% of the sets they can compute, so the gap holds without the review.

The generator itself is reliable. Its rules find usable queries on 152 of the 190 Spider, BIRD and LiveSQLBench databases we tried; the others lack the repeated rows the rules need. When GPT-Sol writes the natural requests of 200 random generated tasks, neither GPT-Sol nor Sonnet gains on its own text. \section{Models Make Choices Without Saying So}
\label{sec:disclosure}
A model that computes both interpretations when each is asked for usually returns only one of them for the open request, and often does not say that there was a choice. Asking for an explanation does not cause this gap. Against the same call asking only for SQL, correct answers to specific requests change by at most nine of 204 per model, and every paired interval includes zero. Nor does the explanation make models raise settled choices. On specific requests, no alternative returns the other interpretation, and at most one of 204 responses per model calls the choice open. Alternatives on other choices, which the sets do not test, appear in 4--20 of 204 responses per model.

\centering\includegraphics[width=\columnwidth]{col_disclosure.pdf}

\textbf{Models return one interpretation where two are correct.} Returning both interpretations is much rarer than returning one correct answer (Figure~\ref{fig:disclosure}). Even among the sets in which a model answers both specific requests correctly, it returns both interpretations for the open request in only 58\% for Sonnet, 48\% for GPT-Sol, 31\% for Haiku and 15\% for GPT-Luna. Accuracy hardly separates the models, whose answers to specific requests are right in 80--98\% of sets, but reporting does. The larger model of each family returns both about two and three times as often as the smaller one, yet none closes the gap. When a model states its interpretation, the statement matches its SQL in 99--100\% of responses. The models describe one calculation correctly without saying that another, equally valid calculation was possible on the same data. The unreported interpretation matters. In 98 of the 204 sets, the two interpretations return different rows, and in the other 106 the same rows with different computed values, so the user gets a different answer in every set.

\textbf{Most misses are failures to report.} Most interpretations a model misses on the open request are ones it can compute. The same model computes the missed interpretation correctly when asked for it alone in 72--94\% of the missed sets (Figure~\ref{fig:decomposition}). Figure~\ref{fig:outcomes} sorts every open request into five outcomes, namely both interpretations returned, the choice named but one interpretation given, one interpretation given silently although the model computes both, a specific request computed wrong, and a specific answer whose SQL does not run. For Haiku and GPT-Luna the most common outcome is the silent one, in which the model can compute both interpretations but gives one without naming the choice, and for Sonnet and GPT-Sol it is the second most common. A score that only checks whether both interpretations appear among the outputs, as top-$k$ coverage~\cite{ambiqt2023} does, cannot tell these outcomes apart. Sampling does not surface the other interpretation either. On 55 randomly drawn sets, five SQL-only samples contain both interpretations in at most 14 for any model, while one explained response from Sonnet does so in 34. What is missing is a prompt to report the choice; SQL-only samples mostly repeat one interpretation.

\textbf{Naming a choice is not the same as giving the other interpretation.} A model that says a choice is open often stops there. Among the sets in which a model names the choice and can compute both interpretations in the same call, it still returns only one interpretation in 10--65\% of them, and GPT-Luna does so most often. Such a response warns the user but leaves them to ask for the other interpretation, a step the model could have taken itself, since it computes that interpretation when asked for it alone.

\textbf{Silent choices follow conventions on our sets, but not on BIRD.}\label{sec:filterresults} On our request sets, when a model settles a choice without saying so, it usually takes the interpretation that benchmark authors take. In 61 tie and counting sets, one interpretation is the convention of BIRD and Spider references (Section~\ref{sec:defaults}), namely a plain \sql{LIMIT} rather than every row tied at the cut-off, and counting joined rows rather than distinct entities. The conventional interpretation is the intended one in 29 of these sets, so the design favors neither. Yet when a model's main answer is one of the two interpretations, it is the conventional one in 76--91\% of cases for every model (Figure~\ref{fig:conventions}). The conventional interpretation is also the simpler SQL, so these data cannot separate habit from simplicity. On BIRD's own tie and counting questions the preference reverses: more answers match the other interpretation (90) than the reference (37; Section~\ref{sec:impact}). Which interpretation a model takes silently thus varies with the request, and a user cannot tell which one an answer computes unless the model says so.

\textbf{Many misses on AMBROSIA are also failures to report.} The pattern is not an artifact of our tests. AMBROSIA pairs each ambiguous question with one unambiguous question per interpretation, and Saparina and Lapata~\cite{saparina2025disambiguate} observe that models usually give one preferred interpretation. We split each missed interpretation into one the model cannot compute and one it computes but does not report. On 120 ambiguous test questions per model, the model computes 49--66\% of the interpretations it misses when asked the unambiguous version (Figure~\ref{fig:decomposition}). Even when a model answers every unambiguous version correctly, it returns all interpretations for the ambiguous question in only 12--28\% of questions. On the 40 vagueness questions per model, which ask which column or value a phrase means, models compute 48--56\% of the interpretations they miss, so the gap also covers the referent-column choices that our request sets leave out. On both benchmarks, models leave open choices unreported, whatever the source of the ambiguity, wording or calculation.

\textbf{Examples.}\label{sec:examples} For the film request of Figure~\ref{fig:teaser}, GPT-Sol states interpretation A, which matches its SQL, but treats the choice as settled; GPT-Luna says the choice is open but gives no second query; Sonnet adds B: ``per-day price defined as the rating's average rental\_rate divided by its average rental\_duration (ratio of averages).'' Responses can also mislead in the other direction. For a specific request that says to drop districts tied with the 10th, Sonnet answers as asked but marks its tie rule as unresolved, a false alarm; for an open count of awards, Sonnet names the choice and gives both \sql{COUNT(*)} and \sql{COUNT(DISTINCT player\_id)}, the two counting units.

\subsection{References follow unstated conventions}
\label{sec:defaults}

\subsection{The unstated interpretation changes answers}
\label{sec:impact}
The choice a reference makes for an open question is not cosmetic. For each open BIRD development question, we apply the library's edit for the other interpretation to the reference SQL wherever it gives a valid interpretation, and run both. Of 664 such questions, 156 (23\%) change their answer (Figure~\ref{fig:impact}). These are one in ten of all BIRD development questions. Counting moves the answer most, often by more than half of its value. For ``How many accounts in North Bohemia has made a transaction with the partner's bank being AB?'', the reference counts joined rows and returns 2,260, while counting each account once returns 55. Ties change about a quarter of answers, often the list of returned items, and join type and missing-value filters change about one in ten. The data behind these choices are common. Every one of the 12 evaluation databases has at least two kinds of data on which an unstated choice changes an answer, such as joins that repeat rows, columns with missing values and maxima shared by several rows.

\textbf{BIRD scores the other interpretation as wrong.} On the 79 questions checked below, accepting both interpretations raises accuracy from 25\% to 57\%; the difference is answers that BIRD counts as wrong SQL, although the question allows them. We ask the four models 137 BIRD development questions on which a tie, counting or join edit of the reference changes the answer, and score each answer against both queries. Two authors checked that the edit gives a valid interpretation of the question, and 79 questions pass. Of the 236 answers BIRD marks wrong on them, 99 return the other interpretation. On tie and counting questions, more answers match the edited reference (90) than the reference itself (37), and on 17 questions every model returns the other interpretation (Table~\ref{tab:answers}).

\section{A Two-Phase Method for Open Choices}
\label{sec:method}
A conversation about an open choice has two moments, before the user says which interpretation they mean and after. Production assistants ask or return one interpretation before (Section~\ref{sec:intro}) and rewrite the request after (Section~\ref{sec:rewrite}). Our method has one phase for each moment, and each step follows from a finding of this paper. Models state their interpretation accurately and almost never call a settled choice open (Section~\ref{sec:disclosure}), so one call can decide whether a choice is open; they compute most interpretations they miss once each is asked for alone, so each gets its own call; and a rewrite keeps the choice but loses other requirements (Section~\ref{sec:rewrite}), so each interpretation is written as the full request and the pick is added as one clause, leaving the rest word for word.

\subsection{Phase 1: decide, then answer}
\label{sec:methoddesign}
Phase 1, \method{Decide-then-answer}, runs before the user replies (Figure~\ref{fig:methodsteps}). First, one call lists the interpretations of the request, each written as the full request with exactly one interpretation; if it lists only one, one more call answers it, and nothing else runs, so a clear request costs two calls and one query. Second, where a choice is open, each interpretation it lists, at most four, is answered in its own call. Third, every answer runs on the database, SQL that fails is dropped, and identical results are shown once. The user sees the first answer with the others as alternatives, and phase 2 starts when the user picks one (Section~\ref{sec:rewrite}). An option, \method{Decide-then-search}, first searches wide in the second step, with two more calls that list the interpretations and then any that are missing, using \method{DtP}'s prompts~\cite{saparina2025disambiguate}, for users who must not miss an interpretation.

\textbf{More interpretations than today's answer, at no loss of precision.} Table~\ref{tab:methods} measures both datasets the same way: coverage, the open requests with every interpretation returned; precision, the share of returned answers that are right on clear or specific requests; and calls. Pooled over both models and paired by item, \method{Decide-then-answer} returns every interpretation for $28.9 \pm 3.5$ points more ambiguous AMBROSIA questions than \method{Single answer} and for $63.1 \pm 3.2$ points more open requests, with no loss of precision ($-0.3 \pm 3.7$ points on AMBROSIA, $+4.4 \pm 2.0$ on request sets), and its main answer is right on 6.3 points more specific requests. Precision holds because the first step finds no open choice in 86--90\% of specific requests, which then get one answer, as from \method{Single answer}. Against \method{Plain}, \method{Three samples} and \method{DtP}, it is the most precise, by 9.4 to 19.2 points on AMBROSIA and 5.9 to 52.0 points on request sets, all significant; it covers more than \method{Plain} and \method{Three samples}, and more than \method{DtP} on request sets, by 42.8 points, where \method{DtP}'s restatements lose other requirements. Only on AMBROSIA does \method{DtP} cover more, by 8.3 points, at 19.2 points less precision and nearly three times the calls, having no step that spots clear questions.

\textbf{Where the gain comes from.} \method{Decide-then-search} is \method{DtP} with the first step added, so their difference isolates that step: the same AllFound ($-1.1$ points) and 14.3 points more precision. The gain is not from returning fewer alternatives. We cut \method{DtP}'s answers, per question, to the number of interpretations that the first step lists. Spent where the first step finds a choice, this budget finds every interpretation on $7.6 \pm 2.0$ points more ambiguous questions than spent on random questions, and \method{Decide-then-answer}, with the same budget, finds $15.0 \pm 2.9$ points more than the cut \method{DtP} at no lower precision. \method{Decide-then-search} finds every interpretation for 7.2 points more ambiguous questions but is 5.0 points less precise, at 2.3 times the calls, so it suits users who must miss no interpretation, whatever the calls cost.

\textbf{Two-turn experiment: fewer user turns than asking.} \method{Clarifying question} needs a second turn, so we test it separately. A simulated user has one interpretation in mind and, when the first turn does not show it, states it in one more turn; the model then answers the specific request, the same second answer for every method. Per 100 requests, with one in five AMBROSIA questions ambiguous, \method{Decide-then-answer} needs $35.0 \pm 3.3$ fewer user turns than \method{Clarifying question} and $14.9 \pm 2.8$ fewer than \method{Single answer}, and $40.8 \pm 2.4$ and $22.1 \pm 2.0$ fewer on request sets. It also ends right on $9.1 \pm 2.2$ and $12.6 \pm 2.5$ more AMBROSIA requests and on $3.4 \pm 0.9$ and $6.1 \pm 1.1$ more request-set requests, because an answer shown in the first turn needs no second answer that can go wrong, at 1.1 to 1.5 more calls per request.

\subsection{Phase 2: keep the request, add the pick}
\label{sec:rewrite}
When the user picks an interpretation, today's systems rewrite the request. Cortex Analyst rewrites each follow-up into a self-contained question~\cite{xu2024cortex}, the Fabric data agent rephrases each question~\cite{fabric2026agent}, LangChain's ConversationalRetrievalChain~\cite{langchain2024crc} and LlamaIndex's CondenseQuestionChatEngine~\cite{llamaindex2024condense} condense each follow-up into a standalone question, and \method{DtP} writes each interpretation as a short question. Each rewrite is a new copy that can lose a requirement, so phase 2 keeps the request and adds the pick as one clause, leaving the rest unchanged.




Request sets test this, as their three requests differ only in the choice. For each interpretation of a request set, the same SQL prompt receives one of four texts: (a) the original specific request; (b) the open request rewritten by the model as one interpretation with \method{DtP}'s prompt, told the intended interpretation; (c) the open request unchanged, followed by a one-sentence description of the interpretation; (d) the open request and the interpretation condensed by the model into a standalone question with LangChain's prompt~\cite{langchain2024crc}; we report 363 interpretations drawn at random from the 204 sets, with all four models and one SQL prompt.

Keeping the request and adding one clause computes 80.7\% of the interpretations correctly, as many as the original specific requests ($p=0.57$, exact McNemar; Figure~\ref{fig:rewrite}). Both rewrites compute fewer, 8.5 points fewer for the interpretation rewrite ($p=0.0004$) and 10.5 for the standalone question ($p<0.0001$), and the loss is largest for Haiku and GPT-Luna. The rewrite seldom loses the choice itself. Of the interpretations answered correctly from the original request and wrongly from the rewrite, the judge finds the choice lost in only 12\%; the rest lose another requirement, most often a formula, an output column or a join (Figure~\ref{fig:rewrite}, right).



\textbf{The same holds on real questions.} We repeat the comparison on 85 BIRD development questions where one library edit of the reference SQL changes the answer. A simulated user follows each question with one sentence that settles the choice, such as ``If several rows tie at the cut-off, return all of them,'' and the edited reference is the gold answer. Over 170 question--model pairs with Sonnet and GPT-Sol, adding the clause beats the standalone question, 58.2\% against 47.6\%. As on our request sets, the rewrite keeps the clarified choice and loses something else; the gap is largest for ties.

\section{Implications}
\label{sec:lessons}
\textbf{Systems could answer open choices instead of asking.} A model states its interpretation accurately and can usually compute the other one, yet seldom reports it. Deciding first, answering each interpretation on its own and executing the answers already adds the other interpretations to an assistant's answer at no loss of precision and saves the user turns that asking costs (Section~\ref{sec:method}).

\textbf{Reporting could be a training target.} The models we test already compute both interpretations of most requests; what they mostly lack is the habit of reporting the second one. Sonnet, the strongest model, still misses it in four of ten sets where it can compute it, so training may help more than scale, and request sets could supply the signal. Each interpretation has its own executable reference, so a reward can credit an open answer only when it returns both interpretations and charge a specific answer for every alternative it adds, which rewards reporting but not guessing.

\textbf{Benchmarks could reward stating assumptions.} Current benchmarks score a single answer per question, which suits questions with one correct interpretation. For a question that leaves a choice open, a complementary practice is to let the model state the assumption it made and the alternative it set aside, and to credit both when each matches its own reference. Request sets make this possible because each interpretation has its own reference, so a benchmark can report accuracy on specific requests, reporting on open requests, and restraint on settled ones.

\section{Related Work}
\label{sec:related}
\textbf{Natural language interfaces to databases.} NaLIR~\cite{nalir2014} fixed ``easy'' ambiguities quietly and, for each ``hard'' one, explained its interpretation and offered several for the user to choose from. Its ambiguities lie mainly in mapping words to schema elements and in how phrases attach. Our results show that the alternatives NaLIR asked users to choose among are now cheap to compute; what is missing is the report. Our method applies NaLIR's interaction to calculation choices and lets execution decide which are ``hard''.

\textbf{Evaluation.} Spider tests generalization across schemas~\cite{spider2018}; BIRD adds large databases and external knowledge~\cite{bird2023}; KaggleDBQA uses realistic databases and documentation~\cite{kaggledbqa2021}; Spider 2.0 tests enterprise workflows~\cite{spider22025}. SParC and CoSQL add context and dialogue~\cite{sparc2019,cosql2019}, and BIRD-INTERACT tests clarification and recovery~\cite{birdinteract2026}. It scores whether a system completes a task after asking the user, whereas request sets score whether it reports a choice it made without asking. TrustSQL rewards a model for abstaining when it cannot answer reliably and penalizes wrong answers~\cite{lee2024trustsql}; request sets reward a different behavior, answering while reporting the open choice. Error detectors flag executable SQL that is wrong against one gold query~\cite{chen2023error}, and verifiers turn such silent failures into abstentions~\cite{alrashed2026verification}; a silent choice passes both, because its SQL is correct for one interpretation. Test suites~\cite{testsuite2020} catch wrong queries whose results match by chance; our concern is the opposite error, in which a correct query for another valid interpretation is rejected because the reference fixes one interpretation. Pourreza and Rafiei re-evaluated top models on Spider and BIRD by hand and found a perfect score out of reach ``due to the multiple interpretations that can be derived from the provided samples''~\cite{pourreza2023evaluating}, and Wretblad et al.\ found noise in BIRD's questions and references whose correction changed which method ranks first~\cite{wretblad2024noise}. We measure the first problem by construction rather than inspection and keep possible reference errors apart from open choices, because a wrong reference and a valid but different one need different fixes.

\textbf{Ambiguous requests.} The closest benchmarks are AmbiQT~\cite{ambiqt2023} and AMBROSIA~\cite{ambrosia2024} (Table~\ref{tab:comparison}). AmbiQT makes Spider questions ambiguous by changing the schema, with synonym columns or tables, split tables and precomputed aggregates, and checks whether both gold queries appear in the top five outputs. AMBROSIA has human-written questions with scope, attachment and vagueness ambiguity on generated databases. Both locate ambiguity in the schema or the wording. The choices behind the conventions of Section~\ref{sec:defaults}, such as ties, counting units, missing values and aggregation level, lie in the calculation, outside both taxonomies. Outside SQL, AmbigQA asks for every plausible answer to an ambiguous question~\cite{min2020ambigqa}, and conversational search studies when a system should ask a clarifying question~\cite{aliannejadi2019asking}. In text-to-SQL the choice often lies in the calculation, where a model can answer fluently without noticing it, so request sets test reporting apart from computing.

\textbf{Generation, SQL methods and semantic layers.} DBPal~\cite{dbpal2020} and GAZP~\cite{gazp2020} generate training pairs for a target database; we also start from the database, but for evaluation. RAT-SQL, PICARD, DIN-SQL, DAIL-SQL, CHASE-SQL and Alpha-SQL~\cite{ratsql2020,picard2021,dinsql2023,dailsql2024,chasesql2025,alphasql2025} improve how the SQL is generated. LookML has developers write each measure ``once, in one place''~\cite{lookml2025}, the dbt Semantic Layer centralizes metric definitions~\cite{dbtsl2025}, and Cortex Analyst generates SQL from them~\cite{cortexdocs2025}. A layer settles the choices its authors foresaw, usually a measure's formula and counting unit; per-request choices, such as ties or the rows a ratio includes, stay open, and these are the choices our method finds and answers for the user.

\section{Conclusion}
\label{sec:discussion}
Text-to-SQL models make choices without saying so. Request sets, which change only one calculation choice, make this visible. Four models compute both interpretations of most sets when each is asked for, yet return both for the open request in only 15--58\% of those sets. Benchmarks cannot see the gap, because their references take one interpretation by conventions that differ by author group; over two in five answers BIRD marks wrong on such questions give the other interpretation. A method that decides first whether a choice is open and answers each interpretation on its own misses fewer interpretations than \method{Plain}, shows far fewer wrong answers than \method{Three samples} and \method{DtP}, adds what \method{Single answer} drops at no loss of precision, needs fewer user turns than \method{Clarifying question}, and keeps the request when the user picks. The models already hold the other interpretation; what is missing is a step that shows it to the user, and a benchmark that asks for it and rewards it. Until then, a plausible number from a text-to-SQL system can answer a different question than the analyst asked, and nothing in the answer says so. We release the request sets, the library of choices, every model response and the code that scores them.

\textbf{Limitations and future work.} The generator covers a subset of analytical SQL, and the library comes from two benchmarks on SQLite, so other benchmarks may hold choice types we have not seen. The request sets cover every choice type on which real references differ, except quantifier, which the generator does not yet build, and referent column, which code cannot read off a reference; for the latter, AMBROSIA's vagueness questions show the same gap. Each request set tests one choice at a time, so requests that leave two choices open at once are not covered. The conventions are read by rules that see one SQL form each, so their counts are lower bounds. One model family wrote the request sets, but the results hold with another writer and without the human review (Section~\ref{sec:specresults}). The BIRD rescoring uses one call per question without exploration, so its shares may shift with stronger prompting. \method{Single answer} and \method{Clarifying question} are rebuilt from the products' documentation, not run on the products, and the two-turn experiment uses a simulated user who always recognizes the interpretation it means. A model judge decides whether a response names the choice, but execution decides every accuracy score and whether both interpretations are returned. Other SQL dialects, longer sessions and a study of how real analysts read and act on a reported choice in their daily reporting work are our planned next steps.
